#Punto de Decisión — Mock, Stub o Fake para Cada Colaborador

1. CitaRepository: Se elige Mock (@Mock con Mockito). El servicio interactúa con la persistencia en dos momentos clave: consulta de datos (entrada indirecta) y actualización de registros (salida indirecta). Mientras que un Stub se limitaría a retornar una lista simulada de citas en findByFechaHoraCitaBetweenAndRecordatorioEnviadoFalse para permitir que el método continúe, no tiene mecanismos para registrar llamadas entrantes ni auditar efectos secundarios. La lógica de negocio exige que, tras el despacho de cada mensaje, la entidad sea marcada con recordatorioEnviado = true y persistida mediante save(cita). Para garantizar que esta mutación ocurrió exactamente una vez por cita y con los argumentos modificados, es obligatorio auditar el comportamiento saliente. Cuando una prueba unitaria requiere suministrar entradas indirectas y simultáneamente verificar salidas indirectas (comandos de actualización), el patrón adecuado según la taxonomía de Test Doubles es un Mock.  
2. ReminderChannelFactory y ReminderChannel: Se elige Mock (@Mock con Mockito). Ambos colaboradores participan en la orquestación del patrón Strategy sin retornar valores computables hacia el exterior del servicio. En el caso de ReminderChannelFactory, el objetivo de la prueba unitaria es asegurar que el servicio aplique el principio de selección correcto: al recibir un paciente con preferencia EMAIL, debe consultar a la fábrica por dicho canal. Si no hay citas pendientes, se debe garantizar que ni siquiera se interactúe con ella (verifyNoInteractions). Y en el caso de ReminderChannel, su método contractual void enviar(Cita, String) es un comando puro con efecto secundario externo (transporte de red/correo). Al tener retorno void, no existe un estado final que pueda validarse mediante assertEquals. La única forma de probar que el servicio cumplió su responsabilidad es corroborar la interacción: verificar que se invocó el método enviar con la instancia de cita correcta y la plantilla de mensaje requerida.
3. Clock: Se elige Fake (Clock.fixed(...) de java.time). Un Fake es un componente que posee una implementación funcional real pero simplificada, lo que lo hace viable para entornos de prueba sin la complejidad del entorno productivo. Clock.fixed no es un simulador pasivo generado dinámicamente por librerías de mocking, sino una subclase concreta y completamente operativa provista por el estándar de Java (java.time.Clock). Configurar un Mockito @Mock Clock requeriría stubbear manualmente múltiples llamadas internas como instant() y getZone(), lo cual genera un acoplamiento frágil a la implementación interna de cómo LocalDateTime.now(clock) resuelve la fecha. Si los métodos del mock no se configuran de forma exhaustiva, el método de fecha puede arrojar NullPointerException o comportamientos inesperados. Al inyectar Clock.fixed(Instant, ZoneId), la máquina virtual opera con su lógica nativa de cálculo de fechas, pero congelada en un instante determinista. Esto erradica la dependencia del reloj del sistema operativo y permite calcular de forma exacta y reproducible la ventana temporal de 24 horas (ahora y en24Horas) en cualquier entorno de ejecución o runner de CI.
